# MCP Clash Guardian v2.4：安全收敛与快速切换计划

> 状态：待审核，尚未实施  
> 日期：2026-08-31  
> 范围：总结当前问题并提出后续改造计划。本文件不授权直接修改运行策略、Clash/Mihomo 配置或 Cloudflared 服务。

## 1. 执行摘要

当前生效策略是 `v2.3-minimal-follow`。它是对旧版激进控制环的一次安全收缩：Guardian 不再做周期 MCP 优化、全组延迟测试、自动重选、策略组改写或批量连接删除，只在以下关键状态变化后重启一次 Cloudflared：

- TUN 从断开恢复为连接；
- Mihomo PID 变化；
- 被监听策略组的最终叶子节点变化并保持稳定。

这条策略比旧版安全，但仍有四个核心矛盾：

1. Guardian 只跟随当前节点，并不保证当前节点是 SG；当前被监听组是手工 `Selector`，所以选 SG 仍依赖用户。
2. 用户明确切换节点后，手工重启 Cloudflared 能立即表达“我已经选完”的意图；自动 watcher 无法知道该节点是否最终稳定，因此需要轮询和 8 秒防抖，实际约 13–16 秒才完成。
3. 自动流程每次稳定节点变化都整体重启 Cloudflared，不先判断连接是否已经对齐，也不在重启后确认 Tunnel 真正 ready。
4. 开机时 Cloudflared、Clash Verge 和 Guardian 没有确定的启动顺序；Guardian 启动时只建立基线，不主动校准，存在漏处理。

本计划不恢复旧版激进控制环。推荐的 v2.4 目标是：

> 保留“关键事件最多重启一次 Cloudflared”的保守基线，增加用户意图快速通道、启动校准、事件合并、全局互斥、冷却与限次、只读路径判断和失败停止。

逐连接迁移和自动 SG 策略属于后续独立阶段，默认关闭，不能与第一阶段同时上线。

## 2. 术语和责任边界

### 2.1 组件职责

| 组件 | 当前职责 | 不应承担的职责 |
|---|---|---|
| Clash Verge | 用户界面、配置管理 | 不应因 Cloudflared 路径陈旧而被例行重启 |
| Mihomo | TUN、路由、策略组和节点选择 | 不应被 Guardian 的应用延迟控制环反复驱动 |
| Cloudflared | 建立公共 Tunnel，将公网请求转发到本地 MCP origin | 不负责选择 Clash 节点 |
| Guardian | 观察 Mihomo/TUN/节点变化，必要时校准 Cloudflared | 不应成为第二个代理调度器 |
| MCP origin | 实际本地 MCP 服务 | 当前项目不管理它的进程生命周期 |

### 2.2 关键语义纠正

Guardian 当前重启的是 **Cloudflared 隧道连接器服务**，不是 Clash Verge，也不是本地 MCP origin。

“未走 SG”可能来自两个不同问题：

1. Mihomo 当前根本没有选择 SG；
2. Mihomo 已经选择 SG，但 Cloudflared 长连接仍停留在旧节点。

Guardian 当前只能处理第二类问题，而且处理方式是整体重启 Cloudflared。它不能保证第一类问题得到解决。

## 3. 当前架构与行为

```text
Windows 启动
├─ SCM 自动启动 Cloudflared（LocalSystem）
└─ 用户登录
   ├─ 登录任务启动 Clash Verge，随后启动 Mihomo/TUN
   └─ 登录任务启动 Guardian（pythonw，Highest）

Guardian 主循环
└─ 每 2 秒读取 TUN、Mihomo PID、Mihomo API、最终叶子节点
   ├─ TUN up / PID 变化：等待约 3 秒
   └─ 叶子节点变化：等待 8 秒稳定确认，最多 2 轮
      └─ stop/start 整个 Cloudflared 服务
         └─ 固定等待 5 秒
```

### 3.1 当前时延

主动切换节点后的自动路径：

| 阶段 | 时间 |
|---|---:|
| 等待下一个轮询发现变化 | 0–2 秒 |
| 节点稳定确认 | 8 秒；连续变化时可能更久 |
| Cloudflared stop/start | 通常约 1 秒，异常时更久 |
| 固定 settle | 5 秒 |
| 总计 | 通常约 13–16 秒 |

本机日志中一次典型完整动作约 14 秒。用户手工重启更快，是因为手工动作本身提供了“选择已经完成，可以立即执行”的明确意图。

### 3.2 当前已经解决的问题

- 用户忘记在稳定节点变化后重启 Cloudflared 时，watcher 可以自动兜底；
- TUN down/up 后可以重建 Cloudflared；
- Mihomo PID 变化后可以重建 Cloudflared；
- 节点短时抖动时不会在第一次观测后立刻重启；
- Cloudflared 停止卡住时有超时和强杀兜底；
- 计划任务可以在用户登录后常驻，并留下状态和事件日志。

### 3.3 当前没有解决的问题

- 自动保证选择 SG；
- 用户明确切换后的低延迟即时应用；
- 开机/登录时确定性地对齐 Cloudflared 路径；
- 判断当前连接是否已经跟随新节点；
- 判断 SCM `Running` 之后 Tunnel 是否真的 ready；
- 判断公网 MCP 是否恢复；
- 零中断迁移 Cloudflared 长连接；
- 注销或尚未登录时的 Guardian 运行。

## 4. 历史高风险行为与根因

旧版的主要风险不是“读取状态”本身，而是将高频观察与网络修改绑定成反馈循环：

```text
全组延迟测试 / MCP 多轮探测
→ 判定路径不好
→ 触发节点重选、连接删除或其他网络修改
→ 网络尚未稳定又开始下一轮检查
→ 再次修改
→ 连接持续震荡
→ 最终可能出现 TUN、代理或整机网络不可用
```

v2.4 必须保持以下原则：

- 观察可以低成本、只读、可重复；
- 网络修改只能由有限的状态边沿或明确用户意图触发；
- 每个事件代次只能执行一次修改；
- 修改失败后停止，而不是不断自救；
- MCP 延迟不能重新成为自动节点选择和网络修改的直接触发器。

## 5. 当前问题清单

### P0-01：当前策略不能保证 SG

当前监听组是手工 `Selector`。Guardian 只读取当前叶子节点，然后让 Cloudflared 跟随。若用户选中的本来就是非 SG 节点，重启 Cloudflared 仍会走非 SG，无法解决全链路高延迟。

### P0-02：启动竞态与漏校准

Cloudflared 是系统自动服务；Clash Verge 和 Guardian 是两个独立登录任务，三者没有启动顺序约束。

Guardian 启动时只把当时的 TUN、PID 和节点作为基线，不执行 startup reconcile。以下情况可能被漏掉：

- Cloudflared 早于 TUN 建立连接；
- Guardian 启动时 TUN 和 Mihomo 已经 ready；
- Guardian 启动时 API 暂时不可用，随后第一次可用节点被静默吸收为基线。

### P0-03：自动路径明显慢于明确手工动作

当前自动路径需要 0–2 秒发现、8 秒防抖和 5 秒固定 settle。用户已经明确完成节点切换时，这些等待大部分只是在弥补 watcher 缺少“用户意图”信号。

### P0-04：稳定节点变化无条件整体重启 Cloudflared

当前流程不检查：

- Cloudflared 连接是否已经走新节点；
- Tunnel 是否健康；
- 是否真的需要重启。

整体重启会同时断开当前 Cloudflared 的全部 HA 连接。它不会主动断开 Clash/TUN，但可能制造短暂的 MCP 502、530 或 1033 窗口。

### P0-05：重启成功只等于 SCM `Running`

当前 stop/start 返回成功后固定等待 5 秒，然后把动作记为完成。它不验证：

- `/ready` 是否成功；
- ready connection 数是否恢复；
- 新连接是否走目标节点；
- 公网 MCP 是否已经恢复。

因此存在“服务进程 Running，但 Tunnel 尚未可用”的假成功。

### P0-06：debounce 可能吞掉最终节点事件

节点在最大防抖轮次内持续变化时，函数返回 `stable=false`。调用方虽然取消本次动作，后续仍可能把最后一个未经确认的候选写入 `last_node`。如果该候选随后保持不变，下一轮因新旧相等而不再触发，最终迁移事件被漏掉。

### P0-07：异常路径缺少统一退避和熔断

- restart 抛异常时，基线可能不更新，下一轮会重新识别同一事件并再次重启；
- SCM 已 Running 但 Tunnel 未 ready 时，基线又会被更新，后续不再恢复；
- 没有“一次事件一次动作”的持久标识；
- 没有全局频率上限和自动熔断状态。

### P0-08：常驻 watcher 与手工命令可能并发操作

Task Scheduler 的 `IgnoreNew` 只限制同一个计划任务实例。`control.py run` 会另起 `watcher.py --once`，可以与常驻 watcher 同时 stop/start Cloudflared。

状态文件写入和日志轮转也没有跨进程互斥。

### P0-09：旧版控制环重新启用会带来整网风险

旧 guardian 路径中的 MCP 多轮探测、全组 delay、节点重选和连接删除代码仍在仓库中。直接切回旧模式或把 `recover()` 整体接入 follow 模式会重新引入已经发生过的反馈循环风险。

### P1-01：整个 watcher 长期以 Highest 运行

只有 Cloudflared 服务启停需要管理员权限，但当前整个 watcher 以 Highest 执行用户可写 Git 工作区中的 Python 源码和依赖，权限面过大。

### P1-02：API 不可用时状态可能仍显示 monitoring

只要 TUN 和 PID 存在，follow 模式可能继续写 `monitoring`，即使监听策略组不存在、命名管道不可用或 API 读取失败。硬编码策略组改名后也可能静默失去跟随能力。

### P1-03：follow 模式不使用无效节点保护

旧 guardian 模式会识别“剩余流量、到期时间、官网”等伪节点；follow 模式没有将这项保护纳入重启决策。若 Selector 误选伪节点，仍可能触发 Cloudflared 重启。

### P1-04：状态可观测性不足

当前 follow 模式中的以下字段长期为空：

- `mcp_ok`；
- `mcp_health_class`；
- `hot_median_ms`；
- `cf_ray`。

同时缺少：

- Cloudflared service PID；
- `/ready` 状态和 ready connection 数；
- 各连接 transport、edge 和 chain；
- selected node 与 reconciled node；
- last transition、last action、last success、cooldown deadline；
- watcher 启动时间、Git SHA 或源代码版本。

### P1-05：空闲循环存在重复采样和高频写盘

每个 2 秒循环会重复执行多次 WMI 和 named-pipe API 查询，并全量覆盖 `status.json`。理论上约 43,200 次状态写入/天，但状态信息仍不足。

### P1-06：Windows CLI Unicode 兼容性问题

默认 GBK 控制台打印包含旗帜 emoji 的节点名时，`control.py status` 和 `control.py logs` 可能抛出 `UnicodeEncodeError`。这直接降低了手工诊断体验。

### P1-07：文档与实际行为冲突

README 和 implementation status 仍有大量 v2.2 描述，包括“先做健康检查、健康则不动、滚动恢复、Limited 权限”。实际 v2.3 是稳定节点变化后整体重启，并以 Highest 运行。

### P1-08：运行代码版本不可证明

状态只记录策略版本字符串，没有记录 Git SHA、源码 hash 或进程启动时间。磁盘文件发生未提交修改后，无法仅通过 status 判断常驻进程加载的是哪个版本。

### P2-01：测试覆盖只到局部函数

现有测试覆盖事件 reason 和 service stop/start，但缺少：

- startup reconcile；
- API 晚就绪；
- debounce 多次变化；
- A→B→C 事件合并；
- 手工 fast path 与 watcher 并发；
- ready 失败；
- 冷却、限次和熔断；
- TCP/HTTP2 fallback；
- 状态原子写入。

## 6. v2.4 设计目标

### 6.1 必须实现

1. 用户明确切换节点后，提供比当前自动防抖更快的单次应用路径；
2. 用户忘记操作时，保留当前保守自动兜底；
3. 登录启动后能自动发现并校准 Cloudflared 路径；
4. 相同节点代次不能重复重启；
5. 任何失败都不能进入无限重启、全组测速或自动重选循环；
6. 不修改 Clash Verge、Mihomo/TUN 或 MCP origin 的进程生命周期；
7. 自动决策主要依赖本地只读状态；
8. 每个阶段可以独立关闭并回退到已验证的 v2.3 行为。

### 6.2 明确非目标

第一阶段不实现：

- 根据 MCP 延迟自动选择节点；
- 恢复旧版全组 delay/reselect；
- 自动重启 Clash Verge 或 Mihomo；
- 自动重启 MCP origin；
- 默认启用逐连接删除；
- 将 Guardian 改成 Windows Service；
- 引入额外对外监听的 HTTP controller。

## 7. 推荐架构：双通道、有界收敛

### 7.1 用户意图快速通道

用户已经在 Clash Verge 完成选择后，通过一个明确动作应用当前节点：

```text
用户选择节点
→ 点击“应用到 MCP Tunnel”或运行 fast-apply
→ 读取当前最终叶子两次，间隔 0.5–1 秒
→ 两次一致且 TUN/PID/API 正常
→ 获取全局 mutex
→ 若该 generation 已处理则 no-op
→ 只重启一次 Cloudflared
→ 等待 /ready，而不是固定 sleep 5 秒
→ 记录 reconciled generation
```

建议先实现一个无节点参数的命令：

```text
python control.py fast-apply
```

它只应用 Clash Verge 当前已经选中的节点，不替用户选择节点。后续若需要，再单独审核“选择节点 + 应用”一体化命令。

快速通道目标耗时：

- 意图确认：0.5–1 秒；
- Cloudflared 重启和 ready：按实际状态返回；
- 正常目标：用户动作后 2–5 秒内完成；
- 超过 deadline：停止并报错，不自动循环。

### 7.2 安全自动兜底通道

自动 watcher 保留当前关键事件：

- startup/API 恢复；
- TUN rising edge；
- Mihomo PID 变化；
- 最终叶子节点稳定变化。

处理流程：

```text
观察到新 generation
→ 进入 STABILIZING
→ 期间所有变化只更新 desired generation
→ 最终节点稳定后检查是否已由 fast-apply 处理
→ 已处理：no-op
→ 未处理：执行一次安全 reconcile
→ 成功后进入 cooldown
→ 失败后进入 degraded，不再自动修改
```

自动兜底可以保留 8 秒防抖，因为它缺少用户意图信号。它的价值是处理用户忘记操作、开机、TUN 恢复和 Mihomo 重启，而不是追求最快响应。

### 7.3 Generation 模型

每次需要收敛的目标由以下信息组成：

```text
generation = mihomo_pid + tun_epoch + selected_leaf
```

规则：

- A→B→C 快速变化只处理最终 C；
- 同一 generation 最多自动修改一次；
- fast-apply 和 watcher 共用同一 generation 记录；
- 处理过程中出现更新 generation 时，在当前安全点结束，不为旧目标继续追加动作；
- `stable=false` 时绝不能更新 `last_reconciled_generation`。

### 7.4 Readiness 与状态来源

自动决策优先使用本地只读信息：

| 信号 | 用途 |
|---|---|
| Windows SCM | 进程是否 Running |
| Cloudflared `/ready` | Tunnel 是否有 ready connections |
| Cloudflared `/diag/tunnel` 或 metrics | 活跃连接数、协议和 edge |
| Mihomo `/connections` | Cloudflared 连接当前 chain |
| Mihomo `/proxies` | 当前目标叶子节点 |

公网 MCP 检查可以作为人工 `doctor` 或低频观测项，但在第一阶段不参与自动重启或节点选择。

### 7.5 修改动作的安全上限

第一阶段保留“整体重启 Cloudflared”这一已验证动作，但增加硬约束：

- 同一 generation 最多一次；
- 自动路径至少 60–120 秒冷却；
- 自动整体重启最多 1 次/5 分钟；
- 自动整体重启最多 3 次/小时；
- 达到上限进入 `circuit_open`；
- 失败后不自动重试；
- 状态不确定时不操作；
- 用户 fast-apply 对同一 generation 默认 no-op，只有明确的诊断命令才能强制执行。

## 8. SG 选择问题的独立方案

SG 选择属于 Mihomo 路由策略，不能与 Guardian v2.4 第一阶段混在一起上线。

### 方案 A：保留手工 Selector + fast-apply

优点：

- 风险最低；
- 用户意图明确；
- 不重新引入自动测速/重选循环；
- fast-apply 可以把应用时间压缩到几秒。

缺点：

- 仍需用户选择 SG；
- 用户忘记选择时只能由现有自动兜底跟随当前节点，不能保证 SG。

### 方案 B：Cloudflared 直连

若当前网络可以稳定直连 `*.argotunnel.com:7844`，将其从普通代理选择中解耦是结构上最简单的方案。必须先做只读连通性与持续稳定性测试，不能直接改线上规则。

### 方案 C：Cloudflared 专用 SG 策略组

若必须通过代理，可以把 `*.argotunnel.com` 路由到独立的 `MCP-TUNNEL` 组。该组只管理 Cloudflared，不影响日常浏览或内容解锁策略。

可以考虑：

```text
MCP-TUNNEL
├─ SG 候选组
└─ 非 SG 灾备组
```

但这仍会引入自动选择，需要单独设计：

- 检查间隔；
- 切换容差；
- 冷却；
- 伪节点排除；
- SG 全部失败时的行为；
- 是否允许自动切回；
- 如何避免 URLTest 抖动。

本计划建议先完成方案 A，再以 dry-run 评估 B/C。未经单独审核，不在 v2.4 第一阶段修改 Mihomo 路由策略。

## 9. 逐连接迁移的定位

现有仓库已经有基于 Mihomo `/connections` 和删除单条 connection 的 rolling refresh 基础代码，但当前 follow 模式没有启用。

考虑到历史上“不断检查、不断断连接”造成的整网风险，v2.4 第一阶段不启用逐连接迁移。

只有满足以下条件后才进入单独试验：

1. startup reconcile、generation、mutex、cooldown 和 circuit breaker 已稳定运行；
2. dry-run 能准确识别 stale connection；
3. 有确定性测试覆盖 UDP/QUIC 与 TCP/HTTP2；
4. 每一步均能证明 ready connection 不会归零；
5. 发生 replacement timeout 时立即停止；
6. 具备一键关闭该功能并回退整体 CF 重启的开关。

即使未来启用，也只能删除 `chain != desired_leaf` 的 Cloudflared stale connection，不能删除所有初始连接，不能触碰普通浏览连接。

## 10. 状态机

建议状态：

```text
STARTING
→ WAIT_DEPENDENCIES
→ OBSERVING
→ STABILIZING
→ RECONCILING
→ VERIFYING
→ HEALTHY
→ COOLDOWN

异常路径：
WAIT_DEPENDENCIES / RECONCILING / VERIFYING
→ DEGRADED
→ CIRCUIT_OPEN（达到自动动作上限）
```

核心规则：

- `OBSERVING` 只能读取；
- `STABILIZING` 只能更新 desired generation；
- 只有 `RECONCILING` 可以修改 Cloudflared；
- `VERIFYING` 只读，失败后进入 `DEGRADED`；
- `DEGRADED` 不得自动再次修改，等待新的真实状态边沿或用户命令；
- `CIRCUIT_OPEN` 只能通过冷却到期或明确人工动作解除。

## 11. 分阶段实施计划

### Phase 0：文档、测试和只读可观测性

不改变网络行为：

- 统一 README、OPERATIONS、implementation status 与真实 v2.3 行为；
- 修复 CLI UTF-8/GBK 输出；
- 增加 `status --json`；
- status 增加 service PID、ready connections、transport、chain、selected/reconciled generation、last action、cooldown、started_at、Git SHA；
- 构造一次 Snapshot，避免同一循环重复查询；
- `/version` 只在启动或 pipe 重连时读取；
- 状态只在变化时写，另加 30 秒 heartbeat；
- 状态使用临时文件 + replace 原子写；
- 为 generation、debounce、cooldown、rate limit、mutex 行为补单元测试。

### Phase 1：确定性的保守自动通道

仍然只使用当前整体 CF restart：

- 修复 debounce 吞事件；
- 引入 desired/reconciled generation；
- 增加 startup/API-recovery reconcile；
- 加跨进程命名 mutex；
- `control.py run` 不再另起无锁盲重启；
- 固定 5 秒 settle 改为 `/ready` 条件等待 + deadline；
- 增加冷却、频率限制和 circuit breaker；
- restart 失败后停止，不自动循环；
- 第一周先支持 dry-run，只记录原本会执行的动作。

### Phase 2：用户意图快速通道

- 新增 `control.py fast-apply`；
- 两次快速读取确认当前叶子；
- 与 watcher 共用 mutex 和 generation；
- 同一 generation 已处理时 no-op；
- 提供桌面快捷方式或固定入口；
- 正常目标为用户动作后 2–5 秒 ready；
- fast-apply 完成后，自动 watcher 不得在 8 秒后重复重启。

### Phase 3：只读 alignment gate

- restart 前读取 Cloudflared chain；
- 已全部对齐目标节点时记录 `no_action`；
- 无法确定时保持当前保守动作策略，或按审核后的 fail-safe 规则不操作；
- 仍不启用逐连接删除；
- 先 dry-run 一周，对比“本来会重启”和“可以安全跳过”的比例。

### Phase 4：SG 路由策略专项

单独审核以下选择：

- 继续手工 Selector；
- Cloudflared 直连；
- 独立 `MCP-TUNNEL` SG 自动组。

该阶段不得与 Phase 1/2 同时首次上线，避免无法区分故障来源。

### Phase 5：选择性逐连接迁移试验

默认关闭，只有在前述安全门槛通过后进行：

- 仅 stale connection；
- 一次一条；
- 每一步等待 ready 恢复；
- replacement chain 必须等于 desired leaf；
- 超时立即停止；
- 完整 CF restart 仍作为人工或有冷却的最后兜底。

## 12. 验收标准

### 12.1 安全性

- 任意自动事件不得重启 Clash Verge、Mihomo/TUN 或 MCP origin；
- 同一 generation 的 Cloudflared 自动重启次数必须为 0 或 1；
- 连续失败不得形成重启循环；
- API、节点或 ready 状态不确定时不得连续修改网络；
- A→B→C 五秒内连续变化只处理最终 C；
- Guardian 失败不得导致普通浏览网络中断；
- circuit breaker 达到阈值后必须停止自动动作并显示原因。

### 12.2 快速通道

- 连续人工切换 20 次，每次 fast-apply 只执行一次；
- fast-apply 正常 p95 完成时间不超过 5 秒；
- fast-apply 后自动 watcher 不重复重启；
- 对同一节点重复点击 fast-apply 默认 no-op；
- ready deadline 失败后返回明确错误，不自动再次重启。

### 12.3 自动兜底

- 忘记 fast-apply 时，稳定节点变化最终能触发一次自动校准；
- startup 时依赖晚就绪能够自动进入 reconcile；
- watcher 启动时路径已对齐则不得重启；
- TUN off/on 和 Mihomo PID 变化各重复测试 10 次，无循环动作；
- debounce 连续变化不会吞掉最终节点。

### 12.4 可观测性和运维

- `status` 在 GBK 与 UTF-8 控制台均不崩溃；
- `status --json` 可被脚本稳定读取；
- 状态新鲜度不超过 30 秒；
- 状态文件写入不超过约 2 次/分钟的 idle heartbeat；
- status 能回答：当前选择、当前连接、是否对齐、最后动作、最后成功、是否冷却、是否熔断、运行代码版本；
- watcher 崩溃后计划任务能按预期拉起，并保留明确错误。

## 13. 回滚方案

每个阶段必须有独立 feature flag：

```text
fast_apply_enabled
startup_reconcile_enabled
alignment_gate_enabled
selective_reconnect_enabled
```

回滚顺序：

1. 关闭新增 feature flag；
2. 恢复 v2.3 的稳定节点变化后单次整体 CF restart；
3. 保留 mutex、限次和状态增强，因为它们只提升安全性；
4. 必要时停止 Guardian 计划任务，回到用户手工重启 Cloudflared；
5. 不自动修改 Clash/Mihomo 订阅和策略组，避免回滚时影响普通网络。

## 16. 建议的首轮实施边界

在本文件通过审核后，建议第一轮只实施：

- Phase 0；

第一轮不实施：

- 自动 SG 策略；

> 日期：2026-09-05

## 0. 结论摘要

1. **日本节点更快的原因不是"日本离 Cloudflare 更近"，而是"家 ↔ 出口 ↔ POP"这一段 RTT 从约 90 ms 降到约 66 ms；而在你当前的测试方式里，这一段被走了两遍。** 两遍 × 24 ms ≈ 48 ms，与你观测到的 180 → 130 ms（约 50 ms）几乎完全吻合。

2. **你的浏览器测试是一次"发夹（hairpin）测量"**：客户端和隧道源点是同一台家用电脑、同一条代理链路，所以家 ↔ 出口这一段被计入 **2 次**。而在真实的 ChatGPT 场景里它只被计入 **1 次**。测试方法本身没有错，但它系统性地放大了"换出口节点"的收益。

3. **实测：Claude Code 这一侧的真实延迟是 ~360 ms，不是 130 ms。** 本次探测确认 Claude Code 所在主机位于**保加利亚（Cloudflare `SOF` POP）**。该路径的主导项是 **欧洲 ↔ 亚洲的 Cloudflare 骨干段（约 291 ms）**，换出口节点对它几乎无效。

4. **切到日本这个决定是对的**，对"家里浏览器"和"ChatGPT（美国）"两个场景都有正收益；只是对 Claude Code 场景收益有限。

5. **本次探测顺带发现 4 个正在生效的实际故障/隐患**（详见第 5 节），其中 2 个会直接影响可用性，且都与延迟无关。它们比继续调节点更值得优先处理。

## 1. 测量方法：如何把一条链路拆开量

你提到"测试方式可能不够精确"。这个判断是对的，但问题不在于精度，而在于**它只能得到一个总数，无法归因**。本次分析使用了一个可以把链路切成两半的方法：

```text
GET /cdn-cgi/trace   →  由 Cloudflare 边缘节点直接应答，不进入隧道
                        因此它只测量：客户端 ↔ POP 的往返

GET /mcp             →  边缘 → 隧道 → 家庭 origin → 原路返回
                        因此它测量：完整链路

两者之差              =  隧道回程段（POP ↔ 出口 ↔ 家庭PC ↔ MCP origin）
```

两个额外的关键信号：

- **`/cdn-cgi/trace` 的 `colo=` 字段**给出客户端命中的 POP 代码；`ip=` 字段给出**出口节点的实际公网 IP**，可用来判断流量是否真的走了代理。
- **响应头 `CF-RAY` 的后缀**（如 `...-NRT`）给出实际服务该请求的 POP。`src/check_mcp.py` 已经在采集它，但 follow 模式下没有落盘（对应 v2.4 计划的 P1-04）。

所有测量都采用**单条 keep-alive 连接连续取样**，第 1 次记为冷启动，其余取中位数，与 `check_mcp.py` 的 warmup/hot 模型一致。

## 3. 延迟模型（并用实测验证）

任意一次**热连接**上的 MCP 往返可以拆成四项：

```text
端到端热延迟 ≈ RTT(客户端 ↔ 客户端POP)          ① 客户端接入段
             + RTT(客户端POP ↔ 连接器POP)        ② Cloudflare 骨干段
             + RTT(连接器POP ↔ 出口 ↔ 家庭PC)    ③ 隧道回程段
             + origin 处理时间                   ④ 本地 MCP
```

**关键点：在你的浏览器测试里，① 和 ③ 是同一条物理路径。**
客户端（Chrome）和隧道源点（cloudflared）都在同一台机器上、走同一条 Clash TUN、同一个日本出口。于是 ② ≈ 0（同为 NRT），④ ≈ 0，模型退化为：

```text
浏览器实测 ≈ 2 × RTT(家 ↔ 出口 ↔ POP)
```

**验证：**

| 出口 | RTT(家↔出口↔POP) | 模型预测 2× | 实测 | 误差 |
|---|---:|---:|---:|---:|
| 日本 | 65.8 ms（实测） | 131.6 ms | 131.6 / 129.1 ms | ~0 |
| 新加坡 | ≈ 90 ms（由 180 ms 反推） | ≈ 180 ms | ~180 ms | ~0 |

模型与实测吻合到个位数毫秒。**这就是"为什么日本更快"的完整答案**：不是 Cloudflare 侧的变化，而是家 ↔ 出口的物理 RTT 变短了 ~24 ms，再被发夹结构放大成 ~48 ms。

### 3.1 冷启动 300+ ms 是另一回事

冷启动的构成与热延迟**完全不同**：

```text
冷启动 ≈ DNS + TCP 握手(1 RTT) + TLS1.3 握手(1 RTT) + 首个请求(1 RTT)
```

这些握手**全部在 Cloudflare 边缘终止**，不进入隧道。实测印证了这一点：

- 家庭侧边缘冷启动 282.5 ms ≈ 4.3 × 65.8 ms（客户端↔POP 的 RTT），与隧道无关；
- 完整链路冷启动 339.3 ms，仅比边缘冷启动多 56.8 ms —— 正好是一个隧道回程 RTT。

**推论：冷启动几乎只由"客户端 ↔ POP 的 RTT × 握手次数"决定。** 因此：

- 优化冷启动 = 减少握手次数（连接复用、TLS 会话恢复 / 0-RTT），**不是**换出口节点；
- 你观察到"两种节点冷启动都是 300+ ms"与模型一致，但模型预测**新加坡的冷启动应当明显更差（约 400 ms 量级）**。下次复测建议把冷/热分别记录，不要合并成"300+"。

## 4. 三个真实场景的差异（全局理解）

这是本次分析最重要的一节：**同一条链路，在三个场景下的瓶颈完全不同。**

```text
场景 A  家里 Chrome（你当前的测试方式）
        家 →[出口]→ NRT →[骨干≈0]→ NRT →[出口]→ 家 → MCP
        家↔出口 计 2 次 ← 发夹

场景 B  ChatGPT web 的 MCP 插件（客户端在美国）
        美国 →[≈0]→ US POP →[骨干 US↔JP]→ NRT →[出口]→ 家 → MCP
        家↔出口 计 1 次

场景 C  Claude Code shell（实测在保加利亚）
        主机 →[3ms]→ SOF →[骨干 SOF↔NRT ≈291ms]→ NRT →[出口]→ 家 → MCP
        家↔出口 计 1 次，但骨干段占绝对主导
```

| 场景 | 主导项 | 当前值 | 换出口节点的收益 |
|---|---|---:|---|
| A 家里 Chrome | 家↔出口 RTT ×2 | **131.6 ms（实测）** | **高**（收益翻倍） |
| B ChatGPT web | US↔JP 骨干 + 隧道回程 | ~175–200 ms（模型估算，未实测） | **中** |
| C Claude Code | 欧洲↔亚洲骨干段 | **~360 ms（实测）** | **低**（骨干段占 81%） |

**结论：**

- 换到日本对场景 A、B 都是正确决定。按同样模型估算，若换回新加坡，场景 B 会劣化约 80–90 ms（美国↔新加坡骨干显著长于美国↔日本）。
- **场景 C 的 360 ms 无法靠换节点解决**，因为其中 291 ms 是欧洲到亚洲的物理距离。对这个场景，正确的优化方向是**减少往返次数**（见 7.4），而不是降低单次往返延迟。
- 场景 B 的数字是**模型估算，未实测**。要拿到真实值，最直接的办法是在 Cloudflare 控制台查看该主机名的 Analytics 按数据中心的请求分布，确认 ChatGPT 侧实际命中哪个 POP。

## 5. 本次探测发现的实际问题（与延迟无关，但优先级更高）

### P1 — Guardian 当前处于"失明"状态（严重）

`runtime/status.json` 显示：

```json
"mihomo_api": { "available": false, "error": "Follow group not found: <配置的组名>" },
"phase": "monitoring"
```

探针确认：Mihomo 当前 18 个策略组中**不存在**配置里写死的 follow 组名。原因是订阅/机场已更换，新订阅的组名体系完全不同。三层配置各写了一个不同的组名：

```text
config/default.json  → 组名 X
config/local.json    → 组名 Y（覆盖 X）
Mihomo 实际存在的组   → 既不是 X 也不是 Y
```

后果：**follow 模式已完全失效**，节点切换后不会再自动重建 Cloudflared；而 `phase` 仍然显示 `monitoring`，不会告警。这正是 v2.4 计划中 **P1-02** 描述的情形，现在已经真实发生。

> **根因是设计问题，不只是配置漂移**：把"要跟随哪个组"写成硬编码组名，意味着每次换订阅都会静默失效。
> **建议改为从事实推导**：Mihomo `/connections` 里 `argotunnel.com:7844` 那几条连接的 `chains` 字段，**本身就是 Cloudflared 当前实际走的节点链**。本次探针已验证该方法可用：
>
> ```text
> host=region1.v2.argotunnel.com  port=7844  network=udp  chains=[JP-A, <嵌套Selector>]
> host=region2.v2.argotunnel.com  port=7844  network=udp  chains=[JP-A, <嵌套Selector>]
> ```
>
> 这个方法与订阅、机场、组名全部解耦，不会因换订阅而失效。

### P2 — 故障转移组选中了伪节点（严重）

`故障转移`（Fallback 类型）当前的选中项是 **`剩余流量：43.73 GB`** —— 一个订阅信息占位条目，不是真实代理。一旦有流量落到该组，必然失败。

仓库里 `config/default.json` 的 `invalid_node_patterns` 已经包含 `"剩余流量"`，但 v2.4 计划 **P1-03** 明确记录：**follow 模式没有接入这项保护**。该隐患现在是实际存在的。

### P3 — 所有地区组已塌缩到同一个日本节点（观测性问题）

探针解析出的嵌套选择路径显示，**每一个地区命名的 Selector 最终都指向同一个共享嵌套 Selector，而它当前选中 JP-A**：

```text
新加坡节点 → <共享Selector> → JP-A     ← 名为"新加坡"，实际走日本
台湾节点   → <共享Selector> → JP-A
香港节点   → <共享Selector> → JP-A
美国节点   → <共享Selector> → JP-A
日本节点   → <共享Selector> → JP-A
自动选择（URLTest，独立） → JP-B        ← 与隧道用的不是同一个节点
```

后果：**地区标签当前全部失真**。以后再做"新加坡 vs 日本"的对比测试时，选择"新加坡节点"不会真的切到新加坡，会得到自相矛盾的结论。这一点务必在下次对比测试前修正，否则所有 A/B 数据都不可信。

### P4 — HA 连接只有 2 条，且存在重启风暴

`cloudflared /ready` 返回 `readyConnections: 2`（cloudflared 常规为 4 条）。`/diag/tunnel` 显示两条连接的 `edgeAddress` 都是 `198.18.x.x` —— 即 Mihomo 的 fake-ip 地址，确认 Cloudflared 完全运行在 TUN 内部。

同时 `runtime/automation.jsonl` 显示明显的重启风暴，例如 2026-09-04 16:08–16:24 的 16 分钟内 Cloudflared 被重启 **9 次**，其中多次的触发原因是 `tun_up` 且 `old_node == new_node`（甚至 `new_node: null`）：

```json
{"event":"cloudflared_follow_event","data":{"reason":"tun_up","old_node":"…","new_node":null}}
```

即 **TUN 抖动导致的空转重启**。每次重启都会丢掉全部 HA 连接并重新握手 —— 这正是"首次请求 300+ ms"和偶发 502/530/1033 的直接来源。对应 v2.4 计划的 **P0-04 / P0-07**。

### P5 — 延迟阈值相对新基线已经过松

`threshold_ms: 200` / `recovery_latency_threshold_ms: 350` 是在新加坡 ~170 ms 基线下定的。日本基线是 **129 ms**，于是：

- 链路劣化到 199 ms（比基线差 54%）仍被判为 `healthy`；
- 阈值失去了预警意义。

### P6 — 文档与实现漂移

`docs/implementation-plan-status.md` 通篇描述 **v2.2-region-priority**（先健康检查、健康则不动、滚动恢复、Limited 权限），而实际生效的是 **v2.3-minimal-follow**（稳定节点变化后整体重启、Highest 权限）。v2.4 计划 **P1-07** 已记录此事，但状态文档至今未同步。

## 6. 回看韩国 v1–v9：它真正的教训

`docs/vps-infrastructure/runbooks/vmiss-kr-sel-intl-basic-migration/` 记录了 V1–V9（韩国直连、WireGuard、HY2、SSH-HY2、FRP-QUIC、韩国出口代理、OpenAI Secure MCP Tunnel）全部停止并归档，理由是"延迟无法充分降低"。

结合本次的分段模型，可以给出比当时更清楚的解释：

**那 9 个版本反复更换的，几乎全是"家 ↔ 出口"这一段的承载方式（协议、隧道、转发器）。** 但：

- 在场景 A 里，这一段确实重要 —— 可它的下限由**物理距离**决定，换协议最多省掉几毫秒的封装开销，救不回中韩与中日之间的地理差；
- 在场景 B / C 里，这一段甚至不是主导项，无论换成什么协议都不会有量级改善。

**教训可以浓缩成一句：先归因，再选型。** V1–V9 消耗的是"换一种承载方式再测总时间"的迭代，而单一总时间无法告诉你该优化哪一段。本文第 1 节的 `/cdn-cgi/trace` 对照法成本极低（两条 curl），却能直接定位瓶颈落在 ①②③ 哪一段。**这个方法应当作为以后任何链路改动的前置动作。**

同时，那批归档里有一条结论今天依然成立且已被本次数据再次确认：`docs/vps-infrastructure/incidents/2026-08-api-domain-and-cloudflared-pop.md` 记录的"cloudflared 连到 LAX POP 导致 400 ms~秒级"，本质就是模型里的 ② 骨干段被拉长。**POP 是动态的，不能写死，但必须被观测。**

## 7. 优化策略（按 ROI 排序）

### 7.0 第 0 层：先修正确性，再谈性能

这一层不追求延迟，但优先级最高 —— 当前有两个故障正在生效。

| # | 动作 | 对应问题 | 风险 |
|---|---|---|---|
| 0.1 | 把 follow 目标从"硬编码组名"改为"从 `/connections` 的 argotunnel `chains` 推导" | P1 | 低（只读推导） |
| 0.2 | follow 模式接入 `invalid_node_patterns`，伪节点不得触发重启、且必须告警 | P2 | 低 |
| 0.3 | Mihomo API 不可用 / follow 目标缺失时，`phase` 必须写 `degraded` 而不是 `monitoring` | P1 | 无（仅状态语义） |
| 0.4 | 修复地区组的嵌套塌缩，让地区标签重新对应真实地区 | P3 | 中（改订阅策略，需单独审核） |
| 0.5 | 同步 `implementation-plan-status.md` 到 v2.3 实际行为 | P6 | 无 |

> 0.1–0.3 与 v2.4 计划的 **Phase 0** 完全一致，可以直接并入那一轮，无需新开计划。

### 7.1 第 1 层：零风险、立刻可做的延迟优化

| # | 动作 | 预期收益 | 说明 |
|---|---|---|---|
| 1.1 | **抑制 `tun_up` 空转重启**：`old_node == new_node` 或 `new_node == null` 时不重启 | 消除大部分 300+ ms 冷启动与偶发 5xx | 直接对应 P4；是当前**收益最大**的一项 |
| 1.2 | **把 `CF-RAY` 后缀与 `readyConnections` 落盘到 status** | 归因能力，非延迟 | v2.4 P1-04；没有它无法判断 ② 段是否劣化 |
| 1.3 | **在同组内挑更快的日本节点** | 约 **−14 ms**（端到端） | 实测 `cp.cloudflare.com` 走另一日本节点时边缘 RTT 为 58.6 ms，比隧道当前节点的 65.8 ms 快 7.2 ms；发夹场景下翻倍 |
| 1.4 | **阈值改为相对基线**（如基线 ×1.3 告警 / ×2.0 判严重），或先手工下调到 160 / 260 ms | 恢复预警能力 | 注意：按 v2.4 原则，阈值**只用于告警与可观测性，不得驱动自动网络修改** |
| 1.5 | **冷/热分别记录**，不再合并成"300+" | 归因能力 | 冷启动归因于握手次数，热延迟归因于路径 |

### 7.2 第 2 层：结构性优化（需先验证）

**2.1 Cloudflared 是否可以不走代理直连？**（对应 v2.4 计划"方案 B"）

这是**结构上最干净**的方案：若成立，③ 段会从"家 → 代理 → 日本出口 → NRT"缩短为"家 → 直连 POP"，同时消除代理对 UDP/QUIC 的影响。

本次**未能测出**直连可行性 —— 探针显示 `region1/region2.v2.argotunnel.com` 均解析为 fake-ip（`198.18.x.x`），且 `1.1.1.1` 与 `cp.cloudflare.com` 的出口 IP 均为日本地址，说明**当前所有流量都被 TUN 捕获，没有任何直连样本**。

建议的只读验证方法（不改线上规则）：

```text
1. 在另一台不挂代理的家用设备（或临时关闭 TUN 的一次性窗口）上
2. 反复取 https://1.1.1.1/cdn-cgi/trace，确认 ip= 是家庭 ISP 地址、记录 colo 与 RTT
3. 用 TCP/UDP 7844 对 region1/region2.v2.argotunnel.com 做长时连通性与丢包观测（建议 ≥24h）
4. 只有在长时稳定性达标后，才考虑把 *.argotunnel.com 单独路由为 DIRECT
```

判定标准建议：直连 RTT < 当前 65.8 ms 且 24 小时内无中断，才值得切换。**中国大陆到 Cloudflare 的直连路径通常不稳定，尤其对 UDP/QUIC，因此预期成功率不高 —— 但验证成本很低，值得做一次。**

**2.2 Cloudflared 传输协议 A/B：QUIC vs HTTP/2**

`/diag/tunnel` 显示当前 `protocol: 1`（QUIC，UDP/7844）。QUIC 经由代理时是**被中转的 UDP**，部分机场对 UDP 的转发质量明显差于 TCP。本次也观测到抖动样本（一次 271 ms，正常为 65 ms）。

可 A/B：`--protocol http2`（改走 TCP/7844）。**注意这会修改服务配置，属于网络变更，需按 v2.4 的灰度与回滚要求执行**，且应同时观察 `readyConnections` 是否从 2 恢复到 4。

**2.3 查清 `readyConnections` 为何只有 2**

cloudflared 常规建立 4 条 HA 连接。只有 2 条意味着冗余减半，任何一次重启或代理抖动都更容易造成短暂 1033。这大概率与代理层的 UDP 会话数/超时有关，值得与 2.2 一起排查。

### 7.3 第 3 层：需要付费或较大改动

| 方案 | 针对场景 | 预期 | 成本/风险 |
|---|---|---|---|
| **Argo Smart Routing** | **C（Claude Code）最受益**，B 次之 | 优化的正是 ② 骨干段，官方口径约 −30%；对 C 的 291 ms 骨干段而言潜在收益最大 | 付费附加功能；建议先开一个月做前后对照 |
| Cloudflare 0-RTT / TLS 会话恢复 | 所有场景的**冷启动** | 冷启动可省 1 个 client↔POP RTT | 控制台开关，低风险；对握手频繁的客户端才有意义 |
| `cloudflared --region` 固定注册区域 | B | 可把连接器 POP 拉近美国 | **不推荐**：会同时把 ③ 段拉长为"美国 POP → 日本出口 → 家"，多半净劣化 |

### 7.4 针对 Claude Code 场景（C）的专门建议

这一段值得单独强调，因为它的优化方向与其他两个场景**完全相反**。

场景 C 的单次往返 **~360 ms 是物理下限附近**，其中 291 ms 是欧洲↔亚洲距离，不可压缩。因此：

> **对 Claude Code，正确的优化目标是"减少往返次数"，而不是"降低单次往返延迟"。**

具体做法：

- 单次调用返回更大粒度的结果（一次读整文件 / 整目录，而不是多次小读）；
- 优先使用 `tree` + 一次 `search`，避免反复的探索性小调用（这一点 homemcp 的服务端说明里已经写明，但在 360 ms/次的实际代价下，它的收益比看上去大得多：省 10 次调用 = 省 3.6 秒）；
- 需要大量文件操作时，**写一个脚本一次性执行**，而不是发起几十次 MCP 往返 —— 本次分析本身就采用了这个模式（两个探针脚本各一次调用，取代了几十次交互式查询）。

```text

  1. /cdn-cgi/trace  冷 + 热中位数  → ① 客户端接入段

  3. 两者之差                        → ③ 隧道回程段

必记环境：
  - Mihomo 实际叶子节点（从 /connections 的 argotunnel chains 读，不要从组名猜）
  - cloudflared readyConnections 与 protocol
  - 测试客户端所在位置（家里 / 美国 / 欧洲——三者不可混谈）
```

## 9. 不建议做的事

1. **不要再用"换出口节点 → 看浏览器总时间"作为唯一评估手段。** 它对场景 A 过度乐观，对场景 C 几乎无效，并且是 V1–V9 走过的老路。
2. **在修复 P3（地区组塌缩）之前，不要做任何"新加坡 vs 日本"的 A/B。** 现在选"新加坡节点"实际走的是日本，数据必然自相矛盾。
3. **不要让 MCP 延迟重新成为自动切换节点或自动改网络的触发器。** 这是 v2.4 计划第 4 节反复强调的历史高风险行为，本文的阈值建议（7.1 的 1.4）也只用于告警。
4. **不要为了追逐几十毫秒而增加链路层数。** 每多一跳都同时增加延迟、抖动和故障面；V1–V9 的归档已经证明了这一点。
